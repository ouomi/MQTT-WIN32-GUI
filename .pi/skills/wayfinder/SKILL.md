# 路径勘探（Wayfinder）

当一个目标很大、信息还不完整，且不适合在一次会话里直接开工时，先画一张会逐步完善的**决策地图**。这项技能的产物是可由后续 Pi 会话继续使用的本地 Markdown 文件，而不是外部议题追踪器。

路径勘探的目的在于找清楚怎么走，不在于抢先完成最终交付。除非地图的“备注”明确把执行也纳入范围，否则每个条目只解决一个决策或为决策获取必要事实；一旦路线已经清楚，就把后续实施交还给用户或单独的实现任务。

## 文件与命名

将地图及其条目保存在项目的 `AI-output/wayfinder/` 下。首次建图时，使用清晰、稳定的文件名；英文可使用短横线，中文名称也可以直接使用，例如：

```text
AI-output/wayfinder/迁移内容索引.md
AI-output/wayfinder/迁移内容索引/选择数据格式.md
```

地图文件是唯一的总索引；每个条目使用一个独立文件保存完整问题与结论。面向用户的叙述、地图和条目中，一律使用条目的标题来指代它。不要用难以理解的数字编号代替标题。

除非用户明确指定，开始新地图前不要主动读取 `AI-output/` 中已有的 Markdown 文件；用户给出地图路径或要求继续某张地图时，才读取那一张地图及当前需要处理的条目。

## 地图格式

新建地图时使用以下结构。保持“已作决定”简短，它只负责索引，详细结论只写在对应条目文件中。

```markdown
# <地图名称>

## 目标

<完成这次路径勘探时应获得的规格、决定或清晰的实施路线；一两句话。>

## 备注

<领域背景、必须遵守的约束、需要查阅的项目文档，以及这张地图是否包含执行工作。>

## 已作决定

<!-- 每行链接到一个已解决条目，只概述结论；详细理由留在条目文件中。 -->

- 暂无

## 当前前沿

<!-- 已明确、尚未解决的问题。只列出不受阻塞的条目。 -->

- 暂无

## 已阻塞条目

<!-- 已明确但还不能处理的问题，并注明阻塞它的条目标题。 -->

- 暂无

## 尚未厘清

<!-- 仍在目标范围内，但目前还无法准确写成一个问题的模糊地带。 -->

- 暂无

## 不在本次范围内

<!-- 已明确排除的工作，以及排除原因。 -->

- 暂无
```

任何包含 `<!-- 这行注释禁止删除 -->` 的行都必须原样保留。

## 条目格式

每个条目对应一次能在一个会话中完成的决策或调查。新建条目时使用：

```markdown
# <条目标题>

**状态：** 待处理
**类型：** 调查｜原型｜讨论｜前置任务
**阻塞于：** 无｜<条目标题>

## 问题

<这个条目要回答的、足够具体的问题。>

## 背景与证据

<只记录理解该问题所必需的上下文、链接或文件路径。>

## 结论

<未解决前留空；解决后记录决定、理由、关键证据和后续影响。>
```

“类型”用于选择合适的推进方式：

- **调查**：查阅项目文件、官方文档或其他可靠资料，以取得决策需要的事实。使用 Pi 可用的读取、搜索或网页获取工具；没有可靠来源时，明确标注不确定性，不要编造结论。
- **原型**：做一个便于讨论的低成本草稿、轮廓或最小代码示例。它不是最终交付；将原型文件路径写回条目。
- **讨论**：需要用户偏好、业务判断或取舍的对话。提出少量能真正改变决定的具体问题，不能替用户决定其应表达的立场。
- **前置任务**：在决策前必须完成、但本身不等于最终交付的工作，例如确认访问权限或取得样本数据。能由 Pi 在当前授权范围内完成的就完成；需要用户操作时给出精确清单。记录完成事实及后续条目需要的路径、位置或数量。

## 绘制地图

用户提出一个模糊而大型的想法时，按以下顺序工作：

1. 先用对话确认目标：这张地图最终要交付什么样的清晰结论、规格或路线。目标决定范围，不能含糊带过。
2. 宽度优先地梳理首批问题：覆盖整个空间，先找出现在就能准确表述的问题和可以立刻推进的第一步；不要过早把未知部分切成细碎任务。
3. 如果路线已经清楚、全部工作明显适合一次会话完成，不要创建地图。说明情况，并询问用户要直接规划还是直接实施。
4. 创建地图文件，填入目标与备注。把仍无法准确表述的问题写进“尚未厘清”。
5. 为已明确的问题创建独立条目文件。先创建所有条目，再根据其“阻塞于”字段将它们分别列入“当前前沿”或“已阻塞条目”。
6. 绘制完成即停止。不要在同一会话里顺手解决某个条目。

## 沿地图推进

用户提供地图路径、指定条目，或要求继续推进时：

1. 先读取地图，确认目标、备注、当前前沿和范围边界。不要为此一次性读取所有条目。
2. 用户指定条目时处理该条目；否则从“当前前沿”选择最靠前的一个。若用户指定的条目仍被阻塞，说明阻塞原因并改选前沿条目，除非用户要求先处理阻塞项。
3. 读取选中条目，并立刻把其状态改为“进行中”。开始实质工作前重新读取地图；若地图已被其他会话更新，以最新内容为准。
4. 只解决这一个条目。按其类型使用 Pi 已提供的工具和当前会话中的用户对话；不要假定存在子代理、技能调用工具、议题追踪器或任何外部自动化。
5. 把答案写入条目的“结论”，将状态改为“已解决”。结论应说明决定、理由、关键证据与对后续问题的影响。随后更新地图：在“已作决定”中添加一行指向该条目的链接，并将它从前沿或阻塞列表中移除。
6. 若结论让原先模糊的区域变得可准确表述，为每个新问题创建条目，并从“尚未厘清”删去相应内容；再更新前沿与阻塞列表。若结论表明某条目超出了目标，将该条目标为“超出范围”，并在地图的“不在本次范围内”记录标题、链接和原因，而不要把它记作已作决定。
7. 如果这次决策已让通往目标的路线完全清楚，明确宣布地图完成，并列出建议交接给实施阶段的内容。

默认每个会话只推进一个条目。这样上下文、结论和后续路线都保持可核对；只有用户明确要求，才扩大到多个彼此独立的调查条目。

## 处理未知与范围

“尚未厘清”不是待办清单。判断标准是：现在能否把问题准确写出来，而不是现在能否回答它。

- 能准确发问，即使暂时被阻塞，也应创建条目。
- 还无法准确发问，就留在“尚未厘清”，等待前沿推进后再细化。
- 已经被决定、已经有活跃条目或明确超出目标的内容，不应出现在“尚未厘清”。

范围外内容不会自动回到地图中。只有用户重新定义目标时，才将其作为一张新地图的起点。
